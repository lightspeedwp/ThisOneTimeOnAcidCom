# Book-site animation and reading-comfort audit

## 1. Objective

Assess purposeful existing motion against book discovery, signup and comfortable reading; propose restraint, not a mandatory effects programme.

## 2. Inputs and scope

[repository instructions](../AGENTS.md); [guideline reading order](../guidelines/README.md); [book brief](../content/book/this-one-time-on-acid-brief.md); [registered routes](../src/app/routes.ts); [package manifest](../package.json).

Inputs: current registered routes, existing motion/CSS/keyframes, actual render environment if authorised, book brief and reduced-motion guidance. Record page/component inventory rather than the old fixed 15-page count.

Read current evidence before following historical path examples. This is a React/TypeScript/Vite book website, not a WordPress runtime or makeup-portfolio rebuild. Retain sourced memoir material without restoring its former page architecture.

## 3. Audit steps

1. For each in-scope current page, inventory entrance, scroll reveal, hover/focus/active feedback, loading, route transitions, form/toggle feedback and decorative effects with trigger, duration, source and inspected state.

2. Check header/mobile navigation, footer, theme control, CTAs, forms, cards, links/tags, overlays, book covers, Journal/events teasers and sourced testimonial sections if present. No new testimonial content or unregistered route is required.

3. Assess simultaneous motion, expensive layout/paint/shadow/filter animation, reflow, repeated work and actual performance evidence. Prefer necessary feedback; do not claim transform/opacity or will-change universally solves performance.

4. Check reading interference, persistent animation, focus visibility, motion reduction, pause/skip needs and any flashing risk. Keep content and controls available with motion disabled; do not retain a mandatory scaling fallback for reduced-motion users.

5. Treat old terminal boot/typewriter, neon flicker, RGB glitch, scan lines, holographic shimmer, cursor trails and grid materialisation as historical proposals, not requirements. Reject flashing or distracting effects against the brief; preserve any demonstrated useful feedback as a separately reviewed option.

6. For each recommendation, name route/state, user benefit, source evidence, accessibility fallback and verification method. Reuse existing components before proposing new wrappers; no quota of five patterns/components, fabricated budgets or implementation durations.

7. Prepare prioritised recommendations separating defects from optional ideas. Record browser/viewport/reduced-motion coverage and any unavailable screen-reader/performance evidence.

## 4. Missing evidence and permission boundaries

If a required source, current requirement, environment or permission is unavailable, identify the affected check and stop that part; do not fabricate a substitute or silently broaden scope. Treat historical totals and completion statements as reported evidence, not current results.

Default to read-only assessment. A request to edit or review this prompt does not authorise its underlying task. Do not edit application files, manuscript, images, guidelines, configuration, trackers or Linear records; execute commands, publish, archive or delete only under separately explicit authorisation. Never use age, zero imports or route absence alone as deletion approval. Preserve protected files and existing image sources.

Use UK English and sentence case while preserving exact quotations and proper nouns. Use he/him for Ash; do not alter other people’s pronouns. Do not invent dates, authors, social accounts, quotes, testimonials, transcripts, counts, progress, performance savings or duration estimates.

## 5. Success criteria

- [ ] Current route/component coverage and actual motion sources are recorded.
- [ ] Recommendations respect restrained art direction, reading comfort and reduced-motion needs.
- [ ] No Nova News identity, obligatory flicker/glitch programme or invented test result remains.
- [ ] Coverage, exclusions and source revisions are recorded; planned, static and executed checks are distinct.
- [ ] Proposed changes and unresolved decisions are presented for approval; no implementation or publication is implied.

## 6. Report output

Return Markdown containing scope/revision, inspected inventory, evidence-linked findings, accepted exceptions, proposed actions and limitations. Record each finding’s path and lines, expected versus observed behaviour, impact, uncertainty and verification needed. Mark checks passed, failed, blocked, not tested or not applicable from evidence; never prefill results.

Drafts stay in the response unless a destination is explicitly approved. If repository report persistence is separately requested, propose a relevant root `reports/{topic}/` path and exact content first; task lists and tracker changes require their own approval. Do not overwrite historical reports, mark work complete automatically or move prompts to `.github/prompts/`.
